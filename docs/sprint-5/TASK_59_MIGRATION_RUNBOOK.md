# Task 59 Migration Runbook

Run commands from the repository root in PowerShell. Values below are local examples only; do not reuse them as production credentials.

## Local database startup

```powershell
docker compose up -d postgres
$env:APP_ENV = 'local'
$env:DATABASE_URL = 'postgresql+psycopg://motion:motion@localhost:5432/motion_capture'
```

Install dependencies if needed:

```powershell
backend\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
```

## Upgrade and inspect

```powershell
Set-Location backend
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic history --verbose
.\.venv\Scripts\python.exe -m scripts.check_database
```

Compile SQL without applying it:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head --sql
```

## Supported rollback and re-upgrade

The current history contains one initial migration. `base` drops all Task 59 tables and is destructive; it is supported for empty/test/local databases, not as a production data-preserving rollback.

```powershell
.\.venv\Scripts\python.exe -m alembic downgrade base
.\.venv\Scripts\python.exe -m alembic upgrade head
```

Production rollback normally means deploy the previous compatible application and apply a forward corrective migration. Never run the destructive base downgrade on production data without an independently approved recovery plan and verified backup.

## Create a future migration

Start PostgreSQL, set `DATABASE_URL`, upgrade to head, then:

```powershell
.\.venv\Scripts\python.exe -m alembic revision --autogenerate -m "describe schema change"
```

Review generated DDL, constraint names, downgrade safety, and metadata diff before committing. Never accept autogenerated destructive changes blindly.

## Initialize and validate the test database

Provision a dedicated PostgreSQL database whose name ends `_test`; never point these commands at local development or production data.

```powershell
$env:APP_ENV = 'test'
$env:TEST_DATABASE_URL = 'postgresql+psycopg://motion_test:test-only@localhost:5432/motion_capture_test'
$env:DATABASE_URL = $env:TEST_DATABASE_URL
$env:RUN_POSTGRES_MIGRATION_TESTS = '1'
Set-Location backend
.\.venv\Scripts\python.exe -m pytest app\tests\test_postgresql_migrations.py -q
```

The test refuses non-`test` environments and database names not ending `_test`. It performs `downgrade base → upgrade head → inspect → downgrade base → upgrade head`, so run this migration test as a serialized CI job. Task 60 repository tests should use unique per-run schemas and transaction rollback through `app.db.testing`.

Run the full backend suite:

```powershell
.\.venv\Scripts\python.exe -m pytest app\tests -q
```

## Diagnose common failures

- `DATABASE_URL is required`: set it explicitly for Alembic/database commands. App import alone does not require it in local mode.
- `must use PostgreSQL`: remove SQLite/in-memory URLs; Task 59 integration is PostgreSQL-only.
- `MIGRATION_POLICY must be require_head`: production/production-like configuration must use the locked policy.
- Connection refused: verify PostgreSQL is running, port/host are correct, and credentials/database exist.
- Authentication failed: use environment-specific credentials; do not put secrets in `.env.example` or Git.
- Revision mismatch: run `alembic current` and `alembic history`; deploy/apply migrations before serving production traffic.
- `database migration policy failed`: apply the reviewed migration to head before starting production; do not bypass `require_head`.
- Unsafe test target refusal: set `APP_ENV=test` and use a disposable database name ending `_test`.
- Migration downgrade fails because of live data: stop; do not force-drop production state. Restore/forward-fix under an approved plan.
